Overview

The coding workflow is the core production path in DigitVA. It takes a synced verbal autopsy submission from intake through coder assessment, optional recode, and optional reviewer secondary coding, producing an authoritative Cause of Death (COD) determination.

Step 1: Pre-Coding Pipeline

Before a submission reaches a coder, it passes through several automated stages:

  1. Sync — submission data is pulled from ODK Central.
  2. Consent check — submissions without valid consent are marked consent_refused and excluded from the coding queue. If ODK data is later updated with valid consent, the submission automatically re-enters the pipeline.
  3. Attachment sync — state becomes attachment_sync_pending while attachments are fetched for the current payload.
  4. SmartVA generation — state becomes smartva_pending. The system attempts to generate SmartVA output. This gate must complete (generate, regenerate, or explicitly fail) before the submission moves forward.
  5. Ready for coding — state becomes ready_for_coding. The submission is now in the coder pool.
Screening: Projects may optionally enable a screening_pending gate where a data manager reviews submissions before they enter the SmartVA pipeline. Screening is project-configured.

Step 2: Starting to Code

Each project uses one of two coder-intake modes:

  • Random allocation (POST /coding/start) — the system assigns one eligible submission from the project pool. The coder does not browse or choose.
  • Pick and choose (POST /coding/pick/<va_sid>) — the coder browses eligible submissions and explicitly starts coding on a chosen case.

Both modes exclude submissions that are not codeable, already finalized, or currently allocated to another coder.

Coder entry is subject to project-level coding gates: coding_enabled, coding_start_date, coding_end_date, and per-site daily_coder_limit. The coding_tester role bypasses these gates for testing.

Once coding starts, the submission enters coding_in_progress and the coder receives a 1-hour allocation.

Step 3: Step 1 (Initial Assessment)

The coding interface displays submission categories in the left sidebar. The coder reviews the VA narrative and supporting data:

  1. Review categories — browse submission data organized by category (demographics, medical history, symptoms, etc.).
  2. Narrative Quality Assessment (NQA) — if the project has NQA enabled, the coder must complete a scored assessment of the narrative quality before proceeding.
  3. Social Autopsy Analysis — if the project has Social Autopsy enabled, the coder must complete a three-level delay factor assessment (decision, reaching care, receiving care) before proceeding.
  4. Submit Step 1 — the coder submits an initial COD assessment via the Step 1 button. The workflow state becomes coder_step1_saved.
Step 1 is not the final COD. It is an intermediate assessment. The submission remains allocated to the coder for completion of Step 2.

Step 4: Step 2 (Final Assessment)

After Step 1 is saved:

  1. Review all categories and initial assessment — the coder revisits the submission data and their Step 1 assessment.
  2. Select ICD-10 cause of death code — the coder searches and selects a specific ICD-10 code. Only codes allowed by WHO VA coding allowability rules are available (see ICD-10 Codes help page).
  3. Submit final COD — the coder submits the final assessment. The workflow state becomes coder_finalized.

Upon finalization, the coding allocation is released and the submission is marked as complete from the coder workflow perspective. Step 1 is preserved alongside the final COD for audit purposes.

Step 5: Recode Window (24 Hours)

After coder finalization, there is a 24-hour recode window during which the coder may reopen the case and change their COD determination.

  • The existing finalized COD remains authoritative until a replacement is saved.
  • NQA and Social Autopsy artifacts persist across recode attempts.
  • Incomplete recode work does not replace the existing finalized COD.

After 24 hours, the submission transitions to reviewer_eligible and the coder can no longer recode.

Step 6: Reviewer Pipeline

Reviewer coding is optional and sample-based. Not every coder-finalized case enters the reviewer track.

  1. Reviewer eligible — after the 24-hour recode window closes, the state becomes reviewer_eligible.
  2. Reviewer coding — a reviewer picks up the case and codes independently. The state becomes reviewer_coding_in_progress.
  3. Reviewer finalization — the reviewer submits their own COD. The state becomes reviewer_finalized.
Reviewer authority: The reviewer final COD takes precedence over the coder final COD. The original coder decision is preserved in history as a superseded record.

Not Codeable

At any point during active coding (states coding_in_progress, coder_step1_saved), the coder can mark a submission as Not Codeable:

  • A structured reason is required.
  • The submission enters not_codeable_by_coder and is excluded from the coder allocation pool.
  • A best-effort update is sent to ODK Central (hasIssues flag).

Separately, a data manager may mark a submission as not_codeable_by_data_manager from the screening or ready pool. This is a data-quality exclusion, not a coding outcome.

Stale Allocation Timeout

Active coding and reviewing allocations older than 1 hour are considered stale and are automatically released:

Session Type On Timeout
First-pass coder Deactivates incomplete artifacts (NQA, Social Autopsy). Resets to ready_for_coding.
Recode session Abandons the recode episode. Preserves the currently authoritative final COD. Resets to coder_finalized.
Reviewer session Deactivates all reviewer artifacts (reviews, NQA, Social Autopsy). Resets to reviewer_eligible.

Timeout cleanup runs hourly as a scheduled background task and also opportunistically when a coder or reviewer starts a new session.

Protected States

The following states are protected from automatic ODK data changes. When ODK data changes for a submission in one of these states, the system does not automatically overwrite the existing COD:

  • coder_finalized
  • reviewer_eligible
  • reviewer_coding_in_progress
  • reviewer_finalized
  • finalized_upstream_changed

For finalized cases where ODK data has changed, the submission enters finalized_upstream_changed and requires manual resolution by a data manager or admin:

  • Accept And Recode — promotes new ODK data, transitions to smartva_pending to rerun SmartVA, then returns to ready_for_coding for recoding.
  • Keep Current ICD Decision — promotes new ODK data but preserves the current COD determination.
