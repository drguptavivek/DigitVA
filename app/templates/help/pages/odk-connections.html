ODK Connections

The ODK Connections panel at /admin/panels/odk-connections lets administrators manage connections to ODK Central servers. Each connection stores the details needed to communicate with an ODK Central instance for data sync, attachment downloads, live form lookups, and review-state write-back.

What Is ODK Central

ODK Central is the server application that collects Verbal Autopsy form submissions from field devices. DigitVA connects to ODK Central over its REST API to download submissions, sync attachments, and write back review states. Each DigitVA project can be linked to one ODK Central connection, and one connection can serve multiple projects.

Creating a Connection

To create a new ODK Central connection, click New Connection in the panel and provide:

Field Description
Name A descriptive label for this connection (for example, "Production Central").
Base URL The full URL of the ODK Central instance (for example, https://odk.example.com).
Email The ODK Central user account email used for authentication.
Password The password for that ODK Central account.

Encrypted Credential Storage

Credentials (email and password) are encrypted using Fernet AES-128 before being stored in the database. Each credential field has its own per-row salt, and a shared pepper is read from the environment at runtime. Plaintext credentials are never persisted to the database.

Testing a Connection

After creating or editing a connection, use the Test Connection button to verify that DigitVA can reach the ODK Central server and authenticate successfully. This sends a lightweight API request to ODK Central and reports success or failure inline.

Assigning Projects to a Connection

Each project must be linked to an ODK Central connection so that sync knows which server to contact. In the ODK Connections panel, you can assign one or more projects to a connection. This mapping is stored in the map_project_odk table.

SSRF Protection

The base URL field is validated to prevent Server-Side Request Forgery (SSRF). Only valid external HTTP/HTTPS URLs are accepted. Internal network addresses and non-HTTP protocols are rejected at validation time.

Per-Connection Pacing and Failure Tracking

DigitVA applies outbound request pacing on each ODK connection to avoid sending bursts of requests to the same ODK Central instance. This is enforced per connection, not globally.

When connectivity or authentication errors occur, DigitVA tracks consecutive retryable failures per connection. After a configurable number of consecutive failures, the connection enters cooldown.

Setting Default Meaning
Minimum request interval 0.5 seconds Enforced delay between consecutive ODK calls on the same connection.
Failure threshold 3 consecutive failures Number of retryable failures before cooldown activates.
Cooldown duration 300 seconds (5 minutes) How long the connection refuses new requests after hitting the failure threshold.

Cooldown Behavior

While a connection is in cooldown:

  • All outbound ODK requests for that connection fail fast without contacting the server.
  • Admin connection tests and live ODK lookups return a cooldown error inline.
  • Background sync skips forms that use the cooled-down connection and logs them as skipped.
  • Forms on other connections continue syncing normally.

A single successful ODK call resets the failure counter to zero and clears cooldown.

Connection Health Visibility

The current health state of each connection is visible in three places:

  • ODK Connections panel — shows consecutive failure count, active cooldown flag, remaining cooldown time, and last failure message.
  • Project Forms panel — shows a cooldown warning banner when the assigned connection is degraded.
  • Sync Dashboard — surfaces active cooldowns and recent failures in the status card so operators can understand why live ODK actions may fail.

Retryable Errors

The following error types count toward the failure threshold:

  • Connection timeouts and connection errors
  • Request timeouts
  • HTTP 401 or 403 responses (authentication or authorization failures)
  • Errors containing keywords such as "token", "expired", "Unauthorized", or "Forbidden"
Cooldown errors themselves are not retryable. They propagate immediately to signal that the connection is being protected, rather than being counted as another failure.

Legacy TOML Fallback

Projects that were configured before the DB-managed connection system was introduced may still use a legacy odk_config.toml file. These projects continue to work, but shared cooldown and pacing are guaranteed only for DB-managed connections. Migrating legacy projects to DB-managed connections is recommended.
