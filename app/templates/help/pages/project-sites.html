Project-Site Associations

The Project Sites panel at /admin/panels/project-sites manages the mapping between sites and projects. This association is a prerequisite for configuring ODK form mappings, running data sync, and enabling coder access.

Why Project-Site Associations Matter

DigitVA uses a scope-based access control model where permissions are granted at the project or project-site level. Before a user can code submissions from a particular site, the following must be in place:

  1. The site must exist in the Sites master table.
  2. The site must be associated with a project through this panel.
  3. An ODK form must be mapped to that project-site pair through the Project Forms panel.
  4. The user must have an access grant scoped to that project or project-site combination.

Without the project-site association, there is no sync target, no form mapping, and no scope boundary for access grants.

Access Control Implications

Access grants in DigitVA follow a hybrid RBAC and ABAC model:

  • Role defines what a user can do (for example, coder, reviewer, data_manager).
  • Scope defines where the user can do it (global, project, or project-site).

Supported scope types:

Scope Type Meaning
Global System-wide access. Only the admin role uses global scope.
Project Access across all sites within that project. Used by project_pi and some coder/reviewer grants.
Project-Site Access to one specific site within one specific project. Used by site_pi, coder, reviewer, and data_manager grants.
The system does not infer broader access from missing values. A grant at the project-site level does not automatically grant access to other sites in the same project. Broader access must be granted explicitly.

Mapping Sites to Projects

In the Project Sites panel:

  1. Select a project from the project list.
  2. Add one or more sites to associate with that project.
  3. Each association can be activated or deactivated independently.

A single site can be associated with multiple projects. For example, site "NC01" might be part of both project "UNSW01" and project "ICMR01", with different ODK form mappings and different access grants for each combination.

Who Can Manage Project-Site Associations

This panel is accessible to both admin and project_pi users:

  • Admin users can manage associations for all projects.
  • Project PI users can manage associations only for their own assigned project.

Effect on the Sync Pipeline

The sync pipeline uses map_project_site_odk as the source of truth for what gets synced. Only active project-site associations with a configured ODK form mapping participate in data sync. If a project-site association is deactivated:

  • The corresponding forms are excluded from the sync loop.
  • Submissions from the deactivated pair are excluded from coder allocation.
  • Existing data and coding artifacts are preserved.

Grant Roles

The following grant roles are available in the system:

Role Scope Capability
admin Global Full system administration.
project_pi Project Project-wide oversight, reporting, and configuration.
site_pi Project-Site Site-specific oversight within assigned projects.
coder Project or Project-Site Start coding, submit COD assessments.
reviewer Project or Project-Site Optional secondary coding after coder recode window.
coding_tester Project or Project-Site Test coding workflow; bypasses coding access gates.
data_manager Project or Project-Site Browse submissions, triage, mark not codeable.
collaborator Project or Project-Site Read-only access to data and reporting.
