Projects

The Projects panel at /admin/panels/projects lets administrators create and manage research projects. Projects are the top-level organizational unit in DigitVA: every site, form mapping, access grant, and submission is scoped to a project.

Creating a Project

To create a new project, click New Project and provide:

Field Description
Name The project name (for example, "UNSW01" or "ICMR01").
Description An optional description of the project's purpose or scope.

New projects default to active status. Projects can be deactivated when they are no longer in active use. Deactivating a project does not delete its data, but it will no longer appear in sync, allocation, or coding queues.

Workflow Toggles

Each project has several workflow-related settings that control how coding operates for all forms under that project.

Coding Intake Mode

The coding intake mode determines how coders receive work:

Mode Behavior
Random Allocation (random_form_allocation) The system automatically assigns the next eligible submission to the coder. The coder does not choose from a browse list. This is the default for new projects.
Pick and Choose (pick_and_choose) The coder can browse a list of eligible submissions and explicitly choose which one to start coding. The list still applies all standard workflow exclusions.
The intake mode is a project-level setting. Changing it affects all coders working on forms within that project. The mode does not change the downstream coding state machine once a case enters active coder workflow.

Narrative Quality Assessment (NQA)

When NQA enabled is turned on, coders are presented with a Narrative Quality Assessment form as part of the coding workflow. NQA allows coders to evaluate the quality of the verbal autopsy narrative. When disabled, the NQA step is skipped entirely for all forms in the project.

Social Autopsy

When Social Autopsy enabled is turned on, coders can complete a social autopsy delay analysis as part of the coding workflow. Social autopsy examines contributing social and health-system factors. When disabled, this section is not shown to coders for forms in the project.

Demo / Training Settings

A project can be flagged as a demo or training project. This has several implications:

  • Demo projects are open to all active authenticated users; no explicit coder grant is required.
  • Coding artifacts created in demo mode are temporary and expire after the configured demo-retention window.
  • After demo-retention cleanup, submissions return to their pre-demo workflow state.
  • Demo coding artifacts do not count toward cumulative coder output metrics.
Demo coding uses the same case-viewing and coding forms as production coding. Demo artifacts are visible immediately after save but are temporary. Ensure that coders understand the difference between demo and production projects.

How Project Settings Affect the Coding Workflow

Project-level settings cascade to every form mapped under the project:

  • The intake mode controls the coder dashboard layout and allocation mechanism.
  • NQA and Social Autopsy toggles determine which steps appear in the coding form.
  • Demo/training flags control access openness and artifact retention behavior.
  • Project active/inactive status determines whether the project's forms participate in sync and coding allocation.

Coding Access Gates

For non-demo projects, coder workflow entry enforces additional gates. These gates are configured at the project-site level in the Project-Site Associations panel:

  • coding_enabled must be true for the project-site.
  • The current UTC date must be on or after coding_start_date (if set).
  • The current UTC date must be on or before coding_end_date (if set).
  • The per-site daily_coder_limit must not be exceeded.
Users with the coding_tester role may bypass these gates for testing purposes. Project PIs and Site PIs do not automatically receive coder access; they need an explicit coder or coding_tester grant to code.

Project Setup Workspace & Organization Mode

Clicking Projects in the top navigation bar (or clicking any project's ID, Name, or Project Setup button) opens the full-width Project Setup Workspace with a quick Project Switcher at the top. For projects using Structure: Organization, the Structure section provides six visual tabs:

  1. 1. Levels: Define the health-system hierarchy tiers (e.g., DH > SDH > CHC > PHC-AAM > SC-AAM > Village) and project-wide Coding scope.
  2. 2. Units: Build or bulk-import the tree of districts, blocks, PHCs, sub-centres, and villages, and set per-unit coding gates.
  3. 3. Cadres & permissions ("Who can do what?"): Use the interactive Question-Driven Setup cards or the full-width Level × Cadre matrix to configure who reports deaths, conducts interviews, supervises interviews, codes VA forms, reviews VAs, or serves as Unit In-charge.
  4. 4. Workers & Scope: Add or edit health workers, auto-detect existing DigitVA users by email or 10-digit mobile number without resetting their password, configure per-worker within-tree or cross-tree coding & supervision units (own unit, peer units, all units at level, or custom subset), and generate a one-scan DigitVA Expo mobile app QR code.
  5. 5. HIV & Malaria Mortality (Id10002 & Id10003): Visually set the epidemiological HIV/AIDS and Malaria mortality levels (High, Low, Very low) for the District (top-level unit) and any specific child units. Child units left as Inherited automatically inherit their nearest ancestor's setting so interviewers are not prompted for those questions during field data collection.
  6. 6. Mentoring & Scientists: Visually link Mentoring Institutes (Medical Colleges, AIIMS, ICMR institutes) to the project's District units and grant their Scientists unit-scoped roles (coder, reviewer, coding_tester, collaborator_pii, or collaborator for counts without names) across selected units.
