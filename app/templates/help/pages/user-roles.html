Access Control Model

DigitVA uses a hybrid RBAC + ABAC access control model:

  • RBAC (Role-Based Access Control) determines what a user can do. Your role defines your capabilities.
  • ABAC (Attribute-Based Access Control) determines where a user can do it. Your scope defines the boundary of your access.

Access is granted only when both the role and the scope match the requested action and target record.

Roles

DigitVA defines the following roles. Roles are additive and do not inherit from each other. Each role has a specific scope type that constrains where it can be applied.

Role Description Allowed Scope Types Landing Page
admin Global system administration. May manage users, projects, sites, project-site mappings, integrations, and all application records. Admin-only workflow actions (such as override-to-recode) rely on global admin membership. global Admin Dashboard (/admin)
project_pi Project Principal Investigator. Project-wide oversight within assigned projects. May view data and reporting across all sites in an assigned project, and perform oversight actions allowed by workflow policy. project Admin panel (project-scoped management)
site_pi Site Principal Investigator. Site-specific oversight within assigned project-site scope. May view data and reporting for assigned sites. A user may hold site_pi grants for many project-site pairs. project_site Site PI Dashboard (/sitepi)
data_manager Data-quality and operational triage role. May browse all submissions in scope, view them in read-only mode, mark submissions as Not Codeable, trigger resync operations, and manage coder/coding_tester/data_manager grants within scope. May not start coding, submit COD, or perform reviewer actions. project or project_site Data Manager Dashboard (/data-management)
collaborator Read-only role. May view data and reporting within assigned scope. May not code, review, perform oversight write actions, or administer configuration. project or project_site Read-only views
coder Coding role. May start coding, resume owned coding, submit coding outcomes, and view coding records when allowed by workflow policy. Only sees submissions whose forms resolve to an active project-site mapping. project or project_site Coder Dashboard (/coding)
coding_tester A grant role that can enter non-demo coding while bypassing normal project-site gates: coding_enabled, coding date windows (coding_start_date, coding_end_date), and daily_coder_limit. Uses the coder landing page and workflow. project or project_site Coder Dashboard (/coding)
reviewer Secondary coding role. May start reviewer coding when allowed by workflow policy, resume owned reviewer coding, and submit reviewer COD outcomes. Reviewer coding opens only after the coder's 24-hour recode window closes. project or project_site Reviewer Dashboard (/reviewing)

Scope Types

Every role grant has an explicit scope type that defines the boundary of access:

Scope Type Meaning Required Data
global System-wide access with no project or site boundary. None (no project_id or site_id needed)
project Access across all sites within a specific project. project_id required
project_site Access to a single site within a single project. project_id and site_id both required
Broad access must be granted explicitly. The system never infers broader access from missing values. A NULL site_id does not imply project-wide access unless the scope type is explicitly set to project.

Role-to-Scope Mapping Rules

Not every role can be combined with every scope type. The allowed combinations are:

Role global project project_site
admin Yes No No
project_pi No Yes No
site_pi No No Yes
data_manager No Yes Yes
collaborator No Yes Yes
coder No Yes Yes
coding_tester No Yes Yes
reviewer No Yes Yes

Authorization Rule

A request is allowed only if all of the following conditions are met:

  1. The user is authenticated and active.
  2. The user has the required role for the requested action.
  3. The target record falls inside one of the user's explicit grant scopes.
  4. Any applicable workflow-specific constraints also pass (for example: allowed language, workflow state, allocation ownership, terminal status).

Workflow constraints narrow access further but they do not replace role and scope checks.

Language Filtering

In addition to role and scope, visibility is also filtered by the user's configured coding language (vacode_language). A coder or reviewer may have form access but still not see a particular submission if the submission's narration language does not match the user's language profile.

Access Examples

Example: Coder with project-site scope

A coder with grant project_site(UNSW01, NC01) can code submissions from site NC01 in project UNSW01. They cannot see submissions from site TR01 in the same project, because the scope does not match.

Example: Coder with project-wide scope

A coder with grant project(UNSW01) can code submissions from all sites within project UNSW01, because the project-level grant covers the entire project.

Example: Site PI with multiple grants

A site PI with grants for project_site(UNSW01, NC01) and project_site(ICMR01, NC01) can see site NC01 data in both projects, but cannot see other sites in those projects unless separately granted.

Grant Administration

Role grants are managed by:

  • Admin — may manage all grants across the entire system.
  • Project PI — may manage project-site mappings and non-global access grants only within explicitly granted projects.
  • Data Manager — may create users and manage coder, coding_tester, and data_manager grants within their own grant scope.
Note: Grant data is stored as explicit user-role-scope assignments in va_user_access_grants. The older JSONB permission structure on the user record (va_users.permission) is being phased out in favor of the grants table. During the transition, some legacy paths still reference both.
