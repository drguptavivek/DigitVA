# Offline PHC Desktop Edition Policy

## Purpose

The **DigitVA Field / PHC Edition** enables health workers and Medical Officers (MOs) at a remote Primary Health Centre (PHC) station to operate offline on a desktop or tablet workstation (Windows, macOS, Linux, Android) using **pure Rust and compiled JavaScript only** (zero Python runtime, zero Docker runtime, zero C/Fortran extensions), and synchronize records with a central DigitVA server either via direct HTTPS (`/api/v1/*` with a device bearer token) or via a signed, hybrid-KEM-sealed `.dvb` bundle ([offline-api-contract.md](../from-server/2026-10-21/policy/offline-api-contract.md), [offline-bundle-and-transfer.md](../from-server/2026-10-21/policy/offline-bundle-and-transfer.md)).

## Scope Boundaries

### Included in the Offline PHC Station Edition

1. **Station Onboarding, Custodian, and Signed Station Config (`digitva-bundle` & `digitva-db`)**:
   - Real fieldwork is ingestable only from an **onboarded** station with a verified **custodian** (`{name, designation, phone, email, onboarded_on, verified_by_user_id}`) and an admin-signed two-line `.station-config` file (`b"digitva-station-config-v1\x00" || line1`).
   - An unprovisioned standalone installation operates strictly as a **local sandbox** (`project_id = 1`, `PHC-STANDALONE`): sandbox data is local-only, never exported as a `.dvb` bundle, and never remapped into a server project.
   - Station roster (`death_reporter`, `interviewer`, `station_supervisor`, `coder`): editable in the standalone sandbox, read-only on a provisioned station (using integer server `user_id`s). A `station_supervisor` role is a roster-level role (never in `/api/v1/me/access`) issued by the server only to a user holding an `interview_supervisor` grant at that site. Every record carries `actor_user_id` and `acting_role`.

2. **Registration-Time DPDP Consent, Identifiers, and Aadhaar Reduction (`digitva-text`, `digitva-db`, `mobile/digitva-collect`)**:
   - **DPDP Consent at Registration**: Respondent consent is captured at death registration (`client_draft_id: null`) before any informant personal data (`informant_name`, `informant_phone`, `informant_phone_2`, `address*`) is saved. The interview reuses the case's granted registration consent and re-asks only when the informant is a different person (`client_draft_id` set). Provisioned projects never fall back to hardcoded notices, purposes, or contacts.
   - **Web-Only Consent Withdrawal & Purge**: Consent withdrawal is recorded on the central web application only. The station receives sorted UUIDs to erase via the `purge` list in the signed station config and in `.dvb` bundle receipts.
   - **Registration Identifiers & Phones**: Validated exactly as the server (`app/services/death_identifier_rules.py`): NFKC, split on Python whitespace (Unicode `White_Space` plus U+001C..U+001F, not JS `\s`), one space between parts, uppercase; length in code points, then `char_type` (null means no restriction), then an anchored full match (`^(?:...)$`) in which `\d`, `\w` and `\s` are ASCII as in re2. `letters_digits_hyphen_slash` excludes spaces. Case replies return `identifiers` as a sorted list (`[{code, label, value}]` for value viewers, `[{code, label, present}]` for `coder`) and `warnings: [{code: "identifier_in_use", field, message}]` without other cases' IDs. Phones follow `app/utils/phone.py`: Python whitespace, hyphens and parentheses are dropped, a leading `+91`, `91` or `0` is dropped when exactly 10 digits remain, and only ASCII digits count (a number typed in Devanagari or other digits is not a phone number, so it cannot get a second blind index); no partial phone digits anywhere.
   - **Shared vectors**: the phone, identifier, `Id10073` and `PII_FIELDS` floor rules are pinned by `tests/fixtures/phone_vectors.json`, `identifier_vectors.json`, `national_id_vectors.json` and `pii_fields_floor.json`, read by the server's Python tests, the station's Rust tests (`digitva-text`) and the app's Jest tests; the Python side is the authority (offline-api-contract.md section 14).
   - **Aadhaar / National ID (`Id10073`)**: Reduced at capture to `XXXXXXXXX` + last 3 ASCII digits (`XXXXXXXXX123`) or `XXXXXXXXXXXX` (`< 3` digits), with `answers_sha256` computed over the reduced text and no Aadhaar hash or full number ever stored.

3. **Station Supervisor Corrections (`death_correction` & `identifiers_set`)**:
   - On a provisioned station, a roster user acting as `station_supervisor` may correct death registration details (`death_correction` / `PATCH /api/v1/intake/deaths/<id>`) **only until the interview is completed** (`409 case_completed` thereafter), and may set registration identifiers (`identifiers_set` / `PUT /api/v1/intake/cases/<id>/identifiers`) both before and after interview completion.
   - Closed cases (`cancelled`, `duplicate`) cannot be modified on the station (`409 case_closed`) and require the web.

4. **Offline SmartVA Scoring & Sealed-Field Exclusion (`digitva-smartva`)**:
   - Pure-Rust in-memory execution of the WHO 2022 -> PHMRC transformation and SmartVA Tariff 2.0 scoring engine (`desktop/crates/digitva-smartva`).
   - Coder views, SmartVA inputs, and station CSV exports strip the union of the 19-field `PII_FIELDS_FLOOR` (`Id10007`, `Id10010`, `Id10010a`, `Id10010b`, `Id10010c`, `Id10017`, `Id10018`, `Id10055`, `Id10057`, `Id10061`, `Id10062`, `Id10070`, `Id10071`, `Id10072`, `Id10073`, `visit_address`, `visit_remarks`, `abha_number`, `abha_address`) and the project's `sealed_field_ids` from the signed station config.

5. **Offline ICD-10 / ICD-11 / DORIS Coding & Unwatermarked MCCD PDF (`digitva-icd11` & `digitva-pdf`)**:
   - Local FTS5 reference catalogs (`mas_icd10_2019_2`, `mas_icd11_mms`, `mas_icd_search_terms`, `mas_va_cause_definitions`, `map_icd_cod_buckets`) and in-process WHO ICD-11 `2.6.0` / DORIS engine (`desktop/crates/digitva-icd11`).
   - **ICD-11 + DORIS in process** (`digitva-r7gr`): in coding mode `icd11_doris` the station runs the WHO ICD-API `2.6.0` and DORIS `1.2.0` assemblies inside its own process (`desktop/crates/digitva-server/src/icd11.rs`). One shared engine starts on a background thread the first time coding needs it (opening a case to code, or any ICD-11 route), never on a request thread and never in `icd10` mode. Start-up takes about 13-15 s on an Apple-silicon Mac; `GET /api/v1/icd11/status` (and `icd11` on `/api/v1/health`) reports `not_started | starting | ready | unavailable`. The station serves the server's `POST /api/v1/doris-clinical/{terms,codeinfo,selection-check,process}/<va_sid>` request and response shapes, and `GET /api/v1/icd11/coding-search/<va_sid>` from the WHO search (rows carry `linearization_uri`). While the engine is starting, or when it cannot start, these answer the server's unavailable contract `503 {schema_version: 1, error: {code: "WHO_API_UNAVAILABLE", message}}` ("Preparing ICD-11…" while starting); coding search falls back to the local catalogue. The guidance routes (`postcoordination`, `postcoordination-options`, `hierarchy`, `related`, `details`) are not ported yet and answer `503 WHO_API_UNAVAILABLE`; the picker shows its own "unavailable" text for those panels and plain code selection still works. `icd10` coding stays on the local catalogue and never loads the engine.
   - **Final save in `icd11_doris`**: the station reprocesses the submitted certificate with its engine (the server verifies a signed proof instead) and refuses as the server's online save does: `422 invalid_doris`, `409 DORIS_PROCESS_EXPIRED`, `409 DORIS_CERTIFICATE_CHANGED` (with the fresh `processing`), `409 DORIS_PROCESS_MISMATCH`, `422 final_blocked` for a conclusive code WHO does not know, `503 who_unavailable`. The saved final (and the bundle's `coding_result.final`) carries the engine's normalized `doris_certificate` (every code with its WHO `LinearizationURI`), `doris_result` and `codedit_result`; the process token and digests are not stored. The server still reprocesses the certificate with the engine it pins (offline-api-contract.md 4.3).
   - **Prerequisites and memory**: the .NET 10 runtime (`Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` 10.x, found through `DOTNET_ROOT` or the standard install paths) and the WHO bundle: `DIGITVA_ICD11_BUNDLE_DIR` (the portable ICD-API assemblies with `ICD-API.dll` and `DigitvaIcd11Bridge.dll`, about 67 MB) and `DIGITVA_ICD11_DATA_DIR` (the 2026-01 index and `DORIS_v2.1_1.2.0` rules, about 480 MB; default `<bundle>/data`, `<bundle>/../data`, then `<bundle>/../icdapi_bundle/data`). The station never downloads a missing bundle. The engine holds about 2.1 GB resident with the bundle's server garbage collector, about 650 MB with `DOTNET_gcServer=0`; the station should be launched with `DOTNET_gcServer=0`. Once the engine has started, its .NET host takes over SIGTERM and SIGINT, so the launcher stops the station with SIGKILL.
   - Deterministic A4 WHO Medical Certificate of Cause of Death (MCCD) PDF generation (`desktop/crates/digitva-pdf`) printed normally **without** a provisional watermark.

6. **Data Protection, SQLCipher Per-User Stores & Sealed `.dvb` Bundles (`digitva-pii`, `digitva-bundle`, `digitva-db`, `digitva-server`)**:
   - **SQLCipher (`bundled-sqlcipher`)**: Local database encrypted at rest using a 256-bit key derived via `HKDF-SHA256` from the OS keystore secret + roster user ID + user PIN (6–16 ASCII digits). Enforces inactivity auto-lock and wipes the user's local store after 5 consecutive wrong PIN attempts (`403 store_wiped_max_pin_attempts`).
   - **PII Envelope (`digitva-pii`)**: Implements [pii-envelope-format.md](../from-server/2026-10-21/policy/pii-envelope-format.md) (`v1:aes256gcm+mlkem768x25519:` DEK wrapping to the server's public key only, `v1:aes256gcm:` value sealing with `record_aad`, and HKDF/HMAC blind indexing).
   - **`.dvb` Bundle Transfer (`digitva-bundle`)**: Writes line-oriented `.dvb` files (JCS manifest line, Ed25519 `b"digitva-bundle-v1\x00"` signature line, and AEAD-sealed record lines in canonical order) and verifies signed server receipts (`b"digitva-receipt-v1\x00"`), deleting local records only upon matching receipt acknowledgement (`received_sha256` verified for interviews).
   - **Loopback Server (`digitva-server`)**: Binds `127.0.0.1` only, requires a constant-time per-launch 256-bit bearer token on every `/api/v1/*` route (GETs included), validates `Host` and `Origin` against DNS rebinding, sends `Cache-Control: no-store` on every reply, and emits zero CORS headers.

7. **Shared App UI on the Station (`mobile/digitva-collect` web export)**:
   - **Case lists**: `GET /api/v1/intake/deaths` and `GET /api/v1/intake/cases` honour the `limit`, `cursor` and `registered` parameters the app sends, with the server's rules (`web_intake_service.reported_deaths_page` / `worklist_page`): `limit` defaults to 50 and is clamped to 1..200, non-numeric is `400 invalid_request`; `registered` is blank or `mine` (the active roster actor's registrations); `cursor` is the opaque `next_cursor` of the previous page (keyset on `death_id`, newest first), malformed is `400`. `counts` (`{total, <state>: n}`) cover the whole list, not the page.
   - **Station-only screens**: the acting-role bar, the `.dvb` transfer card and the station roster render only when the per-launch token is present (`getLocalStationLaunchToken()`); the server build never shows them or calls `/station/*`.
   - **Forms, modules and languages**: the station offers the instruments, modules and languages the project offers on the server, under the same per-project policy and no local override. The signed station config carries each project's `form_options` (the server's form-options body) and the served translations of each offered non-English locale; the station binary embeds the server's composed WHO 2022 definition and serves each project's slice with the server's exact bytes and SHA-256. A config naming a form version the binary does not carry is refused at import (`instrument_version_unsupported`): update the station app. The interviewer picks the interview language from the project's locales in the shared UI, as online (offline-api-contract.md 4.3).
   - **Settings: interview modules and coding mode** (owner decision 2026-10-21, `digitva-7o4h`, `digitva-r7gr`): the station ships with every interview module built in. Settings has an "Interview modules" card (one checkbox per module, default all on) and a "Coding mode" card ("ICD-11 + DORIS", the default, or "ICD-10"). A project policy wins over the local choice: when the imported signed config carries a project's `form_options.enabled_extensions`, the card shows the policy's modules read-only with "Set by your project's setup file" and the station refuses a local change (`409 policy_locked`). The local choice governs only where no policy is present: the standalone sandbox, or a project whose `form_options` lacks `enabled_extensions`. The signed config carries no project coding mode yet, so the coding mode is always the station's own choice. "ICD-11 + DORIS" codes in the server's `unmasked_doris` workspace on ICD-11; "ICD-10" in the server's `unmasked_simple` workspace on ICD-10 (no DORIS). Each saved coding result records the mode it was made in (offline-api-contract.md 4.3).
   - **Home**: `GET /api/v1/me/home` returns one block per device-projected role (death reporter, interviewer, coder, reviewer) with counts from the station's own register and drafts.
   - **Contextual help**: the station serves no help route; the app shows its built-in help without a request.
   - **Supervision tab**: intentionally absent offline. The device projection carries no supervisor powers; a roster `station_supervisor` corrects through the corrections path (item 3).

### Excluded (Central Server Responsibilities Only)

- Unpacking or ingesting `.dvb` bundles, holding server private KEM keys, or sealing at rest with server private keys.
- Authoritative cross-case duplicate matching, workflow routing, or recording consent withdrawals.
- Closed-case corrections and server-level supervision (`supervised_case_condition`).
- Peer-to-peer station federation.
