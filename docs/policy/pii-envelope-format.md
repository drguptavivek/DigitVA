# PII Envelope Format Specification

Language-neutral, byte-exact description of the sealed-value and
sealed-record format implemented by `app/utils/pii_crypto.py`, so a second
implementation (the planned `digitva-pii` Rust crate shared by the Flask
server and the offline PHC desktop) can be proven interoperable in both
directions. Design rationale lives in
[death-registration-identifiers.md](death-registration-identifiers.md),
"Encryption at rest", and [pii-encryption-at-rest.md](pii-encryption-at-rest.md).
This document only states the bytes.

Conformance is proven by the vectors in
`tests/fixtures/pii_envelope_vectors.json` (generated by
`scripts/generate_pii_vectors.py`, checked by `scripts/check_pii_blob.py`).
When this text and `app/utils/pii_crypto.py` disagree, the code and the
committed vectors win and this document is corrected.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Primitives

| Name | Definition |
| --- | --- |
| AES-256-GCM | NIST SP 800-38D, 32-byte key, 12-byte nonce, 16-byte tag appended to the ciphertext |
| ML-KEM-768 | FIPS 203. Private key stored as the 64-byte seed `d \|\| z` (`MLKEM768PrivateKey.from_seed_bytes`); public key 1184 bytes; ciphertext 1088 bytes; shared secret 32 bytes |
| X25519 | RFC 7748. 32-byte private scalar (raw, clamped by the primitive), 32-byte public key, 32-byte shared secret |
| HKDF-SHA256 | RFC 5869. "No salt" means the salt is 32 zero bytes (RFC 5869 section 2.2) |
| HMAC-SHA-512 | RFC 2104 with SHA-512; output 64 bytes |
| `b64u(x)` | base64url (RFC 4648 section 5, alphabet `A-Z a-z 0-9 - _`) **without `=` padding** |
| `u16be(n)` | `n` as 2 bytes, big-endian |
| `lp(x)` | `u16be(len(x)) \|\| x` (a 2-byte length prefix) |
| `\|\|` | byte concatenation |

All text-to-bytes conversions are named explicitly below: **ASCII** (must be
7-bit) or **UTF-8**. No Unicode normalisation (NFC, NFKC or other) is applied
anywhere in this layer; the bytes sealed are the UTF-8 bytes the caller gave.

Constants (ASCII):

| Constant | Value |
| --- | --- |
| `DATA_PREFIX` | `v1:aes256gcm:` |
| `WRAP_ALG` | `aes256gcm+mlkem768x25519` |
| `WRAP_PREFIX` | `v1:aes256gcm+mlkem768x25519:` |
| `COMBINER_LABEL` | `digitva pii kem combiner v1` (27 bytes, **not** length-prefixed) |
| `SUBKEY_INFO_PREFIX` | `digitva-pii-bidx/v1/` |

## 2. Keys

### 2.1 Key id

`key_id` matches `^[A-Za-z0-9_-]{1,16}$` as a full match (no trailing
newline accepted). Generated ids are 12 lowercase hex characters
(`secrets.token_hex(6)`); development keyrings use `dev`; the vectors use
`tv1` and `tv2`. Because of this alphabet a key id never contains `:`, `|`
or `0x00`, which the layouts below rely on.

### 2.2 Private key file

One line of ASCII:

    <key_id>:<b64u(ML-KEM-768 seed, 64 bytes)>:<b64u(X25519 private, 32 bytes)>\n

Readers strip surrounding whitespace, split on `:` into exactly three parts,
and refuse a key id failing 2.1, a seed that is not 64 bytes or an X25519
key that is not 32 bytes. Vectors: `deterministic.test_keys.kem_keys[].private_key_file_text`.

### 2.3 Public key configuration (`PII_KEM_PUBLIC_KEY`)

    <b64u(ML-KEM-768 public, 1184 bytes)>.<b64u(X25519 public, 32 bytes)>

Exactly one `.`; the key id travels separately (`PII_KEM_KEY_ID`). Readers
refuse wrong lengths and bytes the primitives reject as a key. Vectors:
`kem_keys[].public_key_config`; `kem_keys[].mlkem_public_sha256` lets a
second implementation confirm it expands the seed the same way.

### 2.4 Blind index key (`PII_BLIND_INDEX_KEY`)

64 hexadecimal characters (either case accepted on read), i.e. 32 raw bytes.
It is used only as described in section 6.

## 3. Data blob (`value_ciphertext`)

    value_ciphertext = DATA_PREFIX || b64u(nonce || AES-256-GCM(DEK, nonce, plaintext_utf8, AAD))

- `DEK`: 32 random bytes from a CSPRNG.
- `nonce`: 12 random bytes from a CSPRNG, fresh for every field.
- The GCM output is ciphertext followed by its 16-byte tag, so the decoded
  payload is `12 + len(plaintext_utf8) + 16` bytes. An empty plaintext gives
  a 28-byte payload (vector `value-empty`).
- `AAD` is defined by the API in use (sections 5.1 and 5.2).

Example (vector `value-identifier`): plaintext `MCCD/2026/000123` (16 bytes)
gives a 44-byte payload, 59 base64url characters, 72 characters in all.

Reading: split on `:` at most twice, i.e. into `version`, `alg`, `payload`
(the payload is everything after the second `:`). `version` MUST equal `v1`
and `alg` MUST equal `aes256gcm`, byte for byte (vector
`fail-value-prefix-case`). Decode the payload, take bytes 0..12 as the
nonce and the rest as ciphertext with tag, open with the DEK and AAD, then
decode the plaintext as **strict UTF-8**; invalid UTF-8 under a valid tag is a
failure (vector `fail-value-non-utf8`).

## 4. Wrapped DEK (`dek_wrapped`)

### 4.1 Wrapping (needs only the public key)

Given `DEK` and the recipient public key (`key_id`, `pk_m` 1184 bytes, `pk_x`
32 bytes):

1. `(ss_m, ct_m) = ML-KEM-768.Encaps(pk_m)` - `ss_m` 32 bytes, `ct_m` 1088 bytes.
2. Fresh ephemeral X25519 key pair `(esk, epk)`; `ss_x = X25519(esk, pk_x)`.
   `epk` (32 bytes) is the X25519 "ciphertext".
3. `KEK = Combine(ss_m, ss_x, key_id, ct_m, epk, pk_m, pk_x)` (4.2).
4. `wrap_nonce` = 12 random bytes.
5. `wrapped = AES-256-GCM(KEK, wrap_nonce, DEK, WRAP_AAD)` - 48 bytes
   (32 + 16 tag), where `WRAP_AAD = ASCII(key_id || "|" || WRAP_ALG)`, for
   example `tv1|aes256gcm+mlkem768x25519`. The separator is a pipe `|`,
   not `0x00`.
6. Output:

        dek_wrapped = WRAP_PREFIX || key_id || ":" || b64u(ct_m || epk || wrap_nonce || wrapped)

The decoded payload is exactly **1180** bytes:

| Offset | Length | Field |
| --- | --- | --- |
| 0 | 1088 | `ct_m` (ML-KEM-768 ciphertext) |
| 1088 | 32 | `epk` (ephemeral X25519 public key) |
| 1120 | 12 | `wrap_nonce` |
| 1132 | 48 | `wrapped` (AES-256-GCM of the DEK, tag last) |

That is 1574 base64url characters; with `tv1` the whole string is 1606
characters.

### 4.2 KEM combiner

    info = COMBINER_LABEL
           || lp(ASCII(WRAP_ALG))
           || lp(ASCII(key_id))
           || lp(ct_m)          # 1088 bytes
           || lp(epk)           # 32 bytes
           || lp(pk_m)          # 1184 bytes, the RECIPIENT's ML-KEM public key
           || lp(pk_x)          # 32 bytes, the RECIPIENT's X25519 public key
    KEK  = HKDF-SHA256(IKM = ss_m || ss_x, salt = none (32 zero bytes), info = info, L = 32)

Order matters everywhere: ML-KEM secret first in the IKM; fields in the order
shown. The label is raw (no length prefix); every field after it has a
2-byte big-endian length. This is "X-Wing style" only in what it binds: it is
**not** the X-Wing KEM (draft-connolly-cfrg-xwing-kem, SHA3-256, different
label and order); an X-Wing library will not interoperate.

Vector `deterministic.combiner`: `ss_m = 00 01 .. 1f`, `ss_x = 20 21 .. 3f`,
`key_id = k1`, `ct_m = 01 x 1088`, `epk = 02 x 32`, `pk_m = 03 x 1184`,
`pk_x = 04 x 32` gives
`KEK = 57c20aeef040abcf4187948c9617874fb899722f3f8351a83df183596e9e3d11`
(also pinned in `tests/test_pii_crypto.py`). Every positive sealed vector
also carries `intermediate.{ss_mlkem_hex, ss_x25519_hex, kek_hex,
wrap_nonce_hex, dek_hex}`, so each step can be checked on its own.

### 4.3 Unwrapping

1. Split on `:` at most three times into `version`, `alg`, `key_id`,
   `payload`. `version` MUST be `v1` and `alg` MUST be `WRAP_ALG`.
2. Look up the private key for `key_id` among the held keys (current and
   previous); none is a failure (vector `fail-wrap-unknown-key-id`).
3. The decoded payload MUST be exactly 1180 bytes (vectors
   `fail-wrap-truncated`, `fail-wrap-extended`).
4. `ss_m = ML-KEM-768.Decaps(sk_m, ct_m)`; `ss_x = X25519(sk_x, epk)`;
   recompute `pk_m`, `pk_x` from the private key; `KEK` as in 4.2 with the
   `key_id` **from the blob**; open `wrapped` with `WRAP_AAD`.

ML-KEM decapsulation of a tampered `ct_m` does not error (implicit
rejection returns a pseudo-random secret); the failure surfaces at the wrap
tag (vector `fail-wrap-mlkem-ct-flipped`). An implementation MUST NOT rely on
Decaps reporting tampering. Relabelling a blob to another key id that IS held
fails because the key id is in both `info` and `WRAP_AAD` (vector
`fail-wrap-relabelled-key-id`). An all-zero (low-order) X25519 result MUST
be refused; Python's `cryptography` raises, and the vector
`fail-wrap-eph-low-order` fails either way.

### 4.4 Re-wrapping

`rewrap` unwraps with whichever held key wrapped the DEK and wraps the same
DEK to the current public key. Data blobs are untouched, byte for byte
(vector `record-rewrapped-tv2`: the fields of `record-multi` under a new
`dek_wrapped` for `tv2`).

## 5. APIs and their AAD

### 5.1 Per-value API (`encrypt_value` / `decrypt_value`)

One fresh DEK per value; returns `(value_ciphertext, dek_wrapped, key_id)`.
The AAD is opaque bytes chosen by the caller and stored nowhere. The only
caller today, registration identifiers
(`app/services/death_identifier_service.aad`), uses

    AAD = death_id.bytes || identifier_type_id.bytes      # 16 + 16 = 32 bytes, no separator

where `.bytes` is the RFC 4122 big-endian 16-byte form of the UUID (Python
`uuid.UUID.bytes`, not the little-endian `bytes_le`). Vector
`value-identifier`: `death_id = 0d1e0000-0000-4000-8000-000000000001`,
`identifier_type_id = 7e9e0000-0000-4000-8000-000000000002`, `aad_hex`
in the vector.

### 5.2 Record API (`seal_record` / `open_record`)

One fresh DEK per record, shared by all of its fields, each field with its
own fresh nonce:

    record_aad(table, field_id, row_id) = ASCII(table) || 0x00 || UTF-8(field_id) || 0x00 || row_id

No length prefixes: `0x00` separators only, and `row_id` (raw bytes; today
`payload_version_id.bytes`, 16 bytes) runs to the end. Stored form: a map
`{field_id: value_ciphertext}` (a JSONB object in
`map_payload_version_pii.sealed`; key order carries no meaning) plus one
`dek_wrapped` and its `key_id`. An empty map is valid and still has a
`dek_wrapped` (vector `record-empty`).

Values are text. What the text means is the caller's business: the payload
accessor stores each value as its JSON encoding (`json.dumps`, so the name
Asha is sealed as the 6 characters `"Asha"`, quotes included), and an empty
string field is sealed as the empty string (vector `record-empty-string`).

Opening with a field subset (`only`) opens just those names that are present
and skips names not sealed (vector `record-only`). **Implementation-defined:**
when no field is to be opened (empty map, or `only = []`) Python returns `{}`
without unwrapping, so even a garbage `dek_wrapped` passes (vector
`record-only-none-bogus-wrap`, marked `conformance: implementation-defined`;
a stricter reader that unwraps eagerly MAY fail it).

Moving a ciphertext to another table, field or record fails (vectors
`fail-record-other-table`, `-other-row`, `-renamed-field`,
`-swapped-fields`, `-field-from-other-record`).

## 6. Blind indexes (equality search, no decryption)

All outputs are **lowercase hex**.

- **Identifier index** (registration numbers, kept from the first release):

        blind_index(context, v) = hex(HMAC-SHA-512(key = blind_key, msg = context || 0x00 || UTF-8(v)))

  `context` is the identifier type id's 16 UUID bytes; 128 hex characters.
- **Class subkey**:

        subkey(class) = HKDF-SHA256(IKM = blind_key, salt = none, info = ASCII("digitva-pii-bidx/v1/" || class), L = 64)

  `L = 64` takes two HKDF-Expand blocks. `class` is one of exactly `phone`,
  `abha_number`, `abha_address`, `payload-fp` (with a hyphen; there is no
  Aadhaar class); anything else is refused, case-sensitively.
- **Class index**: `class_index(class, v) = hex(HMAC-SHA-512(key = subkey(class), msg = UTF-8(v)))`:
  no context and no separator.
- **Blind key id**: the first 8 hex characters (4 bytes) of
  `hex(SHA-256(blind_key))`, stored beside every class index.

Normalisation (digits only for ABHA numbers, lower-cased trimmed text for
ABHA addresses, the identifier rules in
`app/services/death_identifier_rules.normalise`) happens before these
functions and is outside this format. Vectors: `deterministic.blind_index`
(for the test key, `blind_key_id = f57a3b3e`).

## 7. Errors

- Every failure to open a data blob, a record field or a wrapped DEK (bad
  prefix, unknown version or algorithm, unknown key id, missing private key,
  bad base64, wrong length, failed tag, invalid UTF-8, a moved ciphertext)
  MUST surface as ONE error type with ONE message shape. In Python:
  `PiiCryptoError("PII value could not be decrypted (row <row_ref>, key <key_id>).")`,
  where `<key_id>` is the blob's key id when it matches 2.1, else `?`.
  `scripts/check_pii_blob.py` checks this exact shape for every negative
  vector.
- The message and any log line MUST NOT contain plaintext, ciphertext, a
  base64 payload, a DEK, a KEK, a shared secret or any key material; only the
  caller's row reference and a sanitised key id.
- Key configuration errors (`PiiKeyConfigError`) name the setting, never its
  value.
- The Python reader stops at the first failing field of a record; which field
  failed is not reported.

## 8. MUST NOT

- MUST NOT log, print, return to a client or put in an exception message any
  plaintext, DEK, KEK, shared secret, private key or blind key; the vector
  checker prints counts and ids only.
- MUST NOT reuse a nonce under one key: draw every data nonce and wrap nonce
  fresh from a CSPRNG (12 bytes; at most about 2^32 nonces per DEK).
- MUST NOT reuse a DEK across values (per-value API) or across records
  (record API); a record re-sealed after a change gets a fresh DEK.
- MUST NOT accept a table or field id containing `0x00` when sealing: the
  record AAD has no length prefixes, so `("a\0b", "c")` and `("a", "b\0c")`
  would collide. Python does not check this today; field ids are ODK field
  names and tables are fixed names, so none does.
- MUST NOT compare tags, indexes or key fingerprints with a short-circuit
  equality where an attacker can time it: AES-GCM tag checks are done inside
  the AEAD; any other comparison of secret-derived bytes MUST be constant
  time. (Blind indexes are compared by the database as search keys, by
  design.)
- MUST NOT emit padded or standard-alphabet base64 (section 9).
- MUST NOT seal under a key id whose public key does not match the held
  private key (startup refuses a mismatched pair).
- MUST NOT put real keys or real personal data in vectors.

## 9. Implementation-defined and lenient behaviour

A second implementation MUST produce exactly the bytes above. These points
are where the Python **reader** is more lenient than the format, and a
reader MAY be stricter:

- **base64url decoding.** Python decodes with
  `urlsafe_b64decode(text + padding)` and default `validate=False`, so it
  accepts `=` padding, the standard `+` and `/` characters, non-zero
  trailing bits, and silently discards characters outside the alphabet
  (`:`, `!`, whitespace). A strict reader (for example Rust `base64` with
  `URL_SAFE_NO_PAD`) rejects these. Writers MUST emit canonical unpadded
  base64url; no vector depends on leniency.
- **Data blob split.** `split(":", 2)` makes any further `:` part of the
  payload, which the lenient decoder then drops.
- **Empty `open_record`** never unwraps (section 5.2).
- **DEK cache.** Python caches unwrapped DEKs per request (keyed by the
  `dek_wrapped` string, at most 256 per app context, oldest evicted). Not
  part of the format.
- **Failure ordering.** Which check fails first is not specified; only that
  the result is the one generic error.
- **ML-KEM-1024.** Reserved as a future `alg`
  (`aes256gcm+mlkem1024x25519`); not implemented, so it is a failure today
  (vector `fail-wrap-alg`).

## 10. Vectors and CI

`tests/fixtures/pii_envelope_vectors.json`:

- `deterministic.test_keys`: TEST-ONLY keys `tv1` (current) and `tv2`,
  derived from public labels (`SHA-512` / `SHA-256` of
  `digitva pii envelope TEST VECTOR ONLY ...`), in both the file formats of
  section 2 and hex, plus the test blind key.
- `deterministic.blind_index`, `.combiner`, `.reference` (X25519 RFC 7748
  section 6.1, HMAC-SHA-512 RFC 4231 cases 1 and 2, the pinned ML-KEM-768
  decapsulation vector from `tests/fixtures/mlkem768_kat.json`). This section
  regenerates byte for byte; `tests/test_pii_envelope_vectors.py` checks it.
- `vectors`: blobs sealed by the Python implementation, 14 positive
  (`expect: ok`, with `plaintext` and `plaintext_hex`) and 34 negative
  (`expect: fail`, one input changed, `description` says which). ML-KEM
  encapsulation, ephemerals, DEKs and nonces are random, so regenerating
  changes them; regenerate only when the format changes.
- `rust_to_python`: the shape another implementation emits.

How a Rust CI uses it:

1. **Python to Rust.** Load the file; build the keyring from
   `test_keys` (parse `private_key_file_text` and `public_key_config` with the
   crate's own parsers); for each vector open it (value: `aad_hex`; record:
   `table`, `row_id_hex`, `only`) and assert `plaintext` for `ok` or the
   crate's single error for `fail`; assert `intermediate` step by step when
   debugging; check `deterministic` (blind indexes, subkeys, `blind_key_id`,
   combiner, references). Vectors marked `conformance: implementation-defined`
   MAY be skipped.
2. **Rust to Python.** Seal values and records with the same test keys,
   write `{"format": "digitva-pii-envelope-vectors/v1", "producer": "...",
   "vectors": [...]}` in the same vector shape (`expect: ok` and the
   plaintext sealed; negatives optional), then run
   `python scripts/check_pii_blob.py <file> --keys tests/fixtures/pii_envelope_vectors.json`
   (inside `minerva_app_service`, or any Python 3.13 with `cryptography>=48`
   and `flask`). Exit 0 means Python opened every Rust blob as expected.
